# Known Limitations

Честный список границ применимости Agentalyze и осознанных упрощений — по
всему проекту — от task-suite до инфраструктуры. Это не список багов:
каждый пункт — задокументированное решение или ограничение скоупа, о котором
пользователь должен знать до того, как доверяет цифрам. В духе главного
принципа проекта: «число важнее демо».

## Task suite и верификация

1. **Только локальные HTML-фикстуры.** Suite из 30 задач проверяет агентов на
   статических страницах под собственным HTTP-сервером фикстур. Поведение на
   живых сайтах — с их изменчивой вёрсткой, антиботом, капчами, lazy-loading,
   cookie-баннерами — не тестируется вовсе. Перенос результатов на реальные
   сайты — экстраполяция, а не измерение.

2. **Малый suite = шумные цифры.** 30 задач (по 5 на категорию) — это всё ещё
   маленькая выборка: один флейк модели меняет success rate категории на
   десятки процентов. Отчёты честно предупреждают о малых выборках, но сами
   по себе различия вроде «78% vs 83%» между моделями на этом suite
   статистически не значимы.

3. **Один прогон на комбинацию «задача × провайдер».** `compare` выполняет
   каждую комбинацию ровно один раз: ни повторов, ни оценки дисперсии, ни
   контроля температуры/seed'а у провайдера. Нondeterminism LLM остаётся
   неотфильтрованным шумом в каждом числе отчёта.

4. **Верификатор смотрит только на финальный DOM.** Агент, случайно попавший
   в правильное конечное состояние (угадал кликом), получает `success`; частичного
   зачёта за «почти дошёл» не существует. Обратное тоже верно: правильная
   работа с ошибочной фиксацией результата не спасает от `failure_verifier`.

## Наблюдение страницы (runner)

5. **Наблюдение — упрощённая модель страницы.** Элементы: role + accessible name,
   обрезанные тексты, жёсткие лимиты (150 элементов, 12 000 символов).
   Canvas-приложения, сложные кастомные виджеты вне стандартных ARIA-ролей и
   страницы, превышающие лимиты, агент «видит» неполно. Это осознанный трейд-офф:
   компактное наблюдение против полноты.

6. **Идентификаторы элементов нестабильны между шагами** (`e1`, `e2`, ... заново
   каждый шаг). Это заставляет агента перечитывать наблюдение (реалистично), но
   также означает, что модель, склонная «запоминать» id, будет галлюцинировать
   элементы — таксоному это учитывает отдельным тегом, однако сама по себе
   схема смещает статистику отказов для таких моделей.

## Метрики и анализ

7. **Калибровка уверенности зависит от объёма данных.** ECE считается по бинам
   заявленной confidence против фактических вердиктов; при малом числе задач с
   непустой confidence бины почти пусты, и оценка калибровки ненадёжна. Отчёт
   выставляет предупреждение `low_statistics_warning`, но порог срабатывания —
   эвристика, не гарантия.

8. **Стоимость — по редактируемой таблице цен.** Цены не подтягиваются из API
   провайдеров; устаревшая таблица даёт неверные доллары, а отсутствие записи
   даёт `N/A` («неизвестно», не «бесплатно»). Локальные модели помечаются
   бесплатными вручную (`free: true`).

## Regression-режим

9. **Diff трейсов — структурный, не смысловой.** `regression-check` диффит
    метрики (success rate, шаги, латентность, стоимость), а `inspect
    --diff-trace` дополнительно делает структурное сравнение самих трейсов:
    сопоставляет шаги по номеру, показывает смены инструмента, исхода
    инструмента и состояния DOM и указывает первый номер шага с расхождением.
    Однако смысловой интерпретации причины расхождения («почему агент пошёл
    иначе») нет и не предполагается — это была бы непроверяемая эвристика;
    инструмент сообщает, ГДЕ разошлись последовательности, разбор причины
    остаётся за человеком.

10. **Baseline управляется вручную по умолчанию; авто-режим — opt-in
    удобство.** Указатель baseline хранится в `results/` и переносится в CI
    руками (`set-baseline` + зафиксированный run id) — это основной,
    рекомендуемый способ для гейта. Опциональный `--baseline auto` выбирает
    последний прогон с чистой записью в журнале гейтов
    (`baseline_journal.jsonl`) и потому может замаскировать медленную
    деградацию относительно скользящей базы; осознанного выбора точки отсчёта
    он не заменяет.

11. **Порог чувствительности к деградации: только allowlist, без истории
    прогонов.** Реализована упрощённая версия per-task настройки: опциональный
    `regression.yaml` (`excluded_from_gate`) исключает конкретные шумные задачи
    из подсчёта `regressed_count` и CI-гейта; сами пары при этом остаются
    полностью видимыми в diff с пометкой «excluded from gate». Версия со
    скользящим окном («считать регрессией только после N сбоев из последних M
    прогонов») НЕ реализована, потому что хранилище держит прогоны целиком и
    сравнивает их попарно (baseline vs new) — per-task истории исходов для
    окна просто нет, а её появление требует нового формата хранения истории
    по task_id. Глобальной калибровки порога под шум малых выборок тоже нет
    (см. п. 2): вне allowlist любое ухудшение исхода считается регрессией.

## Инфраструктура и CI

12. **Docker smoke-тесты не запускают реальную оценку внутри контейнера.**
    CI проверяет сборку образа и работу CLI (`--help`, `tasks`); полный eval
    внутри контейнера требует либо ключей платного провайдера, либо Ollama —
    то и дело сознательно вынесено в ручной job / локальный сценарий.

13. **Образ никуда не публикуется** (ни Docker Hub, ни GHCR) — только локальная
    сборка и сборка в CI. Публикация реестра — вне заявленного скоупа;
    мультиархитектурность сверх архитектуры раннера не проверялась.

14. **Ручной e2e-job с реальным провайдером не выполнялся автоматически** и
    требует секрета `OPENROUTER_API_KEY`; его корректность подтверждается
    только при первом ручном запуске.

## Code-agent runner (smolagents `CodeAgent`)

Второй раннер (`agentalyze run/compare --agent-style code`,
`src/agentalyze/runner/code_agent/`) — интеграция с `smolagents.CodeAgent`:
модель пишет Python-код, вызывающий инструменты как обычные функции, вместо
structured tool calls. Реализация — тонкие адаптеры
(`model_adapter.py`/`tool_adapters.py`/`loop.py`) поверх существующих
`Provider`/`do_*`/`RunTrace`; сама библиотека (парсер код-блоков, исполнение,
промпты) не переписывается.

15. **Опциональная тяжёлая зависимость, отдельный extras.** `smolagents` не
    входит в основные зависимости — `pip install -e ".[code-agent]"`
    (зафиксировано `smolagents[docker]>=1.21,<2` в `pyproject.toml`, с верхней
    границей мажорной версии, чтобы будущий breaking-релиз библиотеки не
    сломал интеграцию молча). Чистый tool-calling-путь этот пакет не
    импортирует вообще (ленивые импорты в `orchestration/suite_runner.py` и
    `runner/cli.py`).

16. **`executor_type="docker"` (и `e2b`/`modal`/`blaxel`) СЕЙЧАС НЕ РАБОТАЕТ с
    браузерными инструментами этого проекта — подтверждено кодом и живым
    прогоном, не предположением.** Все «удалённые» executor'ы smolagents
    воссоздают каждый `Tool` внутри песочницы вызовом БЕЗ аргументов —
    `{ToolClassName}()` (`smolagents.tools.get_tools_definition_code` /
    `instance_to_source`); адаптеры этого проекта (`tool_adapters.py`)
    требуют `(ctx, recorder)` — живую Playwright `Page` и владеющий ею event
    loop, которые невозможно сериализовать в песочницу. Проверено вживую с
    реальным локальным Docker-демоном: `executor_type="docker"` собрал образ,
    поднял контейнер — и повис: `agent.run()` не вернулся, ни одного
    `ActionStep` не было записано, прогон просто ждал до истечения
    `timeout_seconds` задачи (`FAILURE_TIMEOUT`), без единой ошибки где-либо.
    Поэтому `code_agent/loop.py` теперь явно и быстро отказывает
    (`NotImplementedError` до какого-либо обращения к Docker) при попытке
    использовать любой из этих четырёх режимов — вместо того чтобы тихо
    сжирать весь бюджет времени задачи. **Дефолт настройки
    `AGENTALYZE_CODE_AGENT_EXECUTOR_TYPE` — `"local"`**, не `"docker"` (в
    отличие от первоначального плана задачи, который предполагал обратное,
    не проверив это на реальном коде инструментов).

17. **`executor_type="local"` — НЕ граница безопасности.** Собственная
    документация `smolagents.LocalPythonExecutor` прямо говорит: это не
    security-sandbox. `code_agent/loop.py` пишет warning в лог при каждом
    использовании `"local"`. Единственный оправданный сценарий для этого
    режима сегодня — разработка и тесты с `FakeProvider`/детерминированным
    скриптовым провайдером, который никогда не генерирует непроверенный
    реальный код (см. `tests/runner/code_agent/`). Запускать `"local"` с
    реальной моделью на непроверенных задачах небезопасно.

18. **Реальная сетевая изоляция под Docker не проверена и не может быть
    проверена сегодня** — прямое следствие п. 16: раз ни одна из задач suite
    не может реально выполниться под `executor_type="docker"` с текущими
    адаптерами, тест на «сгенерированный код не может достучаться до
    постороннего домена из контейнера» бессмысленно писать как проверку
    изоляции — писать его не для чего. `tests/runner/code_agent/
    test_docker_executor.py` вместо этого проверяет сам fail-fast guard
    (без Docker). Чтобы `docker`/`e2b`/`modal`/`blaxel` заработали, адаптеры
    инструментов нужно переархитектурить как RPC/HTTP-мост между
    хост-процессом (держит живой Playwright) и песочницей (получает только
    сериализуемые запросы) — это отдельная, нетривиальная задача, не
    сделанная здесь.

19. **Гранулярность шага при code-generation — реконструкция, не факт
    смолагентс.** `smolagents.ActionStep` — один раунд «модель написала код
    → код выполнился», а не один инструмент; один код-блок может вызвать
    несколько инструментов или ни одного. `code_agent/loop.py` разбирает
    раунд обратно на отдельные `StepEvent` (по одному на реальный вызов
    инструмента, как в ReAct-раннере) через `ToolCallRecorder`, сопоставляя
    записи вызовов с `ActionStep.timing` по временной метке — это точное
    сопоставление (оба пишутся из одного потока в строгом порядке
    выполнения), а не эвристика, но сам факт реконструкции стоит знать при
    чтении трейсов code-раннера.

20. **Не вся failure-таксономия одинаково информативна для code-стиля.**
    Существующие теги (`LOOPING`, `WRONG_TOOL_CHOICE`,
    `TOOL_ERROR_MISHANDLED` и др.) применяются к трейсам обоих раннеров без
    изменений (см. `analysis/failure_taxonomy.py`) и остаются осмысленными,
    поскольку code-раннер по-прежнему пишет `StepEvent.tool_call` с реальным
    именем и аргументами инструмента на уровне отдельного вызова (п. 19).
    Два новых тега, `code_execution_error` и `unparseable_code_response`,
    применимы только к code-раннеру (сгенерированный код упал при
    исполнении / smolagents не смог распарсить код-блок вообще —
    различаются по классу исключения `smolagents.utils.AgentError`).

21. **Сравнительный прогон (`examples/code_agent_vs_tool_calling_report.md`)
    — не то же самое, что бенчмарк smolagents, и явно помечен как
    FakeProvider-прогон.** 30 задач Agentalyze — не тот набор задач и не тот
    домен, на котором smolagents измеряли своё «~30% меньше шагов»; цифры
    отчёта — честный результат конкретного прогона на конкретном наборе
    задач с детерминированным скриптовым провайдером (без реального вызова
    модели — оплачиваемые вызовы LLM без явного разрешения пользователя в
    этом проекте не делаются), не универсальное утверждение про
    code-generation вообще. Прогон с реальным провайдером — на усмотрение
    пользователя отдельным запуском `agentalyze compare --agent-style code`.
