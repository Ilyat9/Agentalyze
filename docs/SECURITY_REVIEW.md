# Security Review — HTTP API (продакшн-развёртывание)

Ревью новых эндпоинтов по OWASP API Security Top 10 на момент релиза
сервисного режима. Формат: что проверено (и где в коде), что осталось как
известный риск. Границы самой методологии эвала — в
`docs/KNOWN_LIMITATIONS.md`; здесь только про эксплуатацию сервиса.

## Проверено

### API1:2023 — Broken Object Level Authorization
- Все ресурсные эндпоинты (`/runs/{id}`, `/runs/{id}/report`) отдают статус
  и отчёты ЛЮБОМУ валидному ключу без проверки владельца. Это осознанно:
  модель угроз — «доверенная команда», прогоны — общие артефакты, а не
  приватные объекты. В ответе нет данных, которых нет на общем диске.
  При появлении мультитенантности — добавить `owner` в `suite_runs` и
  проверку в обработчиках (место помечено в `api/auth.py`).

### API2:2023 — Broken Authentication
- Bearer-ключи; хранение — scrypt (n=2^14) + соль, сравнение constant-time
  (`api/auth.py: hash_api_key / verify_api_key_hash`). Плейнтекст не
  хранится и не логируется, показывается оператору один раз при создании.
- 401 не различает «нет заголовка» / «битый ключ» (не помогает перебору);
  при промахе добавлен dummy-scrypt для сглаживания тайминга.
- Отключение auth (`AGENTALYZE_API_AUTH_REQUIRED=false`) — только для
  локальной разработки; в k8s/compose манифестах явно включено.

### API4:2023 — Unrestricted Resource Consumption
- Rate-limit на `POST /runs` per-key (slowapi/limits), 429 + Retry-After.
- Глобальный семафор одновременных прогонов
  (`MAX_ACTIVE_SUITE_RUNS`) — защита памяти/CPU Chromium даже для
  авторизованных клиентов, поверх rate-limit'а запросов.
- Pre-flight health-check провайдеров до старта платного прогона.

### API3:2023 — Broken Object Property Level Authorization / API6 — Unrestricted Access to Sensitive Business Flows
- Провайдеры передаются ТОЛЬКО именами из серверного providers.yaml;
  `base_url`, ключи, модели клиентом не задаются → SSRF через параметры
  запроса невозможен by construction. Отдельно зафиксировано: SSRF-guard
  агента (`runner/tools.py`, navigate) защищает агента внутри задачи и НЕ
  является защитой API-сервера — эта поверхность закрыта тем, что API не
  принимает URL вообще. Если когда-нибудь появится «кастомный base_url в
  запросе» — обязательны allowlist хостов и ревью (помечено как запрет).

### API7 — Server Side Request Forgery
- См. выше: произвольных URL в запросах нет. `/health` ходит только к
  сконфигурированным на сервере провайдерам.

### API8:2023 — Security Misconfiguration
- Секреты (ключи провайдеров) не доступны через API ни в каком виде:
  модели запросов принимают только имена; ошибки возвращают sanitized
  detail (тип исключения вместо стектрейса/путей); `/metrics` не содержит
  секретных лейблов.
- Path traversal: `suite_run_id` используется как компонент пути к отчёту —
  явная проверка `/` и `..` в `app.py:get_report` + тест
  `test_path_traversal_in_report_id_blocked`.
- Контейнер работает под non-root (pwuser), образ не содержит секретов.

### API9:2023 — Improper Inventory Management
- OpenAPI-схема (`/docs`) актуальна автоматически; версии API — в пути
  деплоя, не в коде (одна версия сейчас).

## Осталось как известный риск (осознанные компромиссы)

1. **In-process исполнение прогонов**: при >1 реплике прогон живёт в той
   реплике, которая приняла POST; падение реплики теряет незавершённый
   прогон (статус останется running). Митигация: replicas=1 сейчас; путь
   роста — брокер задач. Не уязвимость, но SPOF надёжности.
2. **Rate-limit in-memory per-replica** (slowapi default): за балансировщиком
   лимиты считаются на каждую реплику отдельно. При replicas>1 фактический
   лимит умножается на число реплик. Митигация при росте: Redis-storage у
   limits.
3. **Статические API-ключи без ротации по расписанию** — достаточна для
   доверенной команды; компрометация лечится revoke-api-key (мгновенно).
   Аудит-лог использования ключей не ведётся (только submitted_by в прогонах).
4. **/health раскрывает имена настроенных провайдеров и их доступность**
   аутентификации не требует (стандарт для probes). Имена — не секреты,
   но если это недопустимо для вашей сети: закройте /health ingress'ом.
5. **Нет mTLS между ingress и pod** — трафик внутри кластера в plaintext.
   Стандартная практика для внутренних namespace; добавьте NetworkPolicy /
   service mesh при требованиях zero-trust.
6. **Markdown→HTML конверсия отчётов** использует python-markdown без
   санитайзера: отчёты генерируются самим сервером из трейсов, но текст
   трейсов включает ответы LLM (потенциально prompt-injected HTML).
   Конверсия включена extension'ом tables только; браузерный XSS-риск
   остаточный — при публичной раздаче HTML добавить санитайзер
   (bleach/nh3) или Content-Security-Policy на ingress.
